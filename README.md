# TCC eClearance System
Torres Capitol College — Web-Based Student Clearance System

Stack as required: **HTML + CSS + JavaScript** (frontend) + **Python (Flask) + SQLite** (backend/database).
Theme + logo from `tcc_logo.jpg` (black shield / silver metallic).

- **Student + Faculty login** with role tabs (`/login`) + registration (`/register`)
- **Student requests clearance** → one click sends to all 16 offices (plus the 9 subject instructors for 2nd Year)
- **Faculty approves/declines** with remarks + **e-signature** (draw on canvas, type a name, or upload a picture of a signature — stored as a base64 image in SQLite). Subject instructors see their own subject queue and sign each assigned subject.
- **Student sees who signed**: each office and subject row shows instructor name, ID, remarks, date + signature image
- **Status is live on the dashboard**: after all assigned offices and subject instructors e-sign, the clearance shows **Cleared** and students can check it anytime
- **Printing is locked until cleared**: the certificate cannot be printed or opened until all assigned signatories have signed (`/certificate/<id>` refuses incomplete clearances)
- **Completed → printable certificate** (`/certificate/<id>` → `window.print()` → Save as PDF) with both office and subject-instructor signature blocks
- If declined → notify + revise & resubmit flow

## Deploy to Render

This folder is a self-contained project root: `app.py`, `requirements.txt`, and `render.yaml` sit at the top level. Push **this folder** to a GitHub repository, not its parent. If you must push a parent folder, set the Render service's **Root Directory** to `web` and point the Blueprint setup at `web/render.yaml`.

### 1. Push to GitHub
```bash
cd ~/chandy/chantot/web
git init
git add .
git commit -m "TCC eClearance"
git branch -M main
git remote add origin https://github.com/<you>/<repo>.git
git push -u origin main
```
`credentials.txt`, the local `eclearance.db`, and `__pycache__/` are gitignored.

### 2. Create the Blueprint
Render Dashboard → **New** → **Blueprint** → select the repository. Render reads `render.yaml`, which creates:

- a Python web service running `gunicorn` (1 process, 8 threads — safe for SQLite)
- a **1 GB persistent disk** mounted at `/var/data` for `eclearance.db`
- a generated `SECRET_KEY` (stable across deploys)
- health checks on `/healthz`
- the Singapore region

When Render prompts for `FACULTY_SIGNUP_CODE`, enter a code if faculty should be able to self-register, or leave it blank to keep faculty signup closed to the public.

> The persistent disk requires a paid instance (`0.5c-512mb`, about $7/month). Disks are not available on the free plan.

### 3. First boot
`init_db()` runs automatically when the web process starts. It creates the database, applies the schema, and seeds the demo accounts because `SEED_DEMO_ACCOUNTS=1`. Open:

```
https://<your-service>.onrender.com/healthz   →  {"status":"ok"}
```

### Free-plan alternative (demo only)
If you do not want to pay for a disk:

1. In `render.yaml`, change `plan` to `free` and delete the `disk:` block.
2. Delete `DB_PATH=/var/data/eclearance.db` (or set it to `eclearance.db`).
3. Deploy. The app works, but **all clearances, signatures, and accounts reset** whenever the service redeploys, restarts, or spins down after inactivity.

For production, keep the disk or move to Render Postgres (which requires changing the SQLite data layer).

### Environment variables

| Variable | Default | Purpose |
| --- | --- | --- |
| `SECRET_KEY` | Dev key locally; generated by Render | Signs session cookies and CSRF tokens. Keep stable. |
| `DB_PATH` | `./eclearance.db` | SQLite file. On Render: `/var/data/eclearance.db`. |
| `APP_TIMEZONE` | `Asia/Manila` | Timezone for signature timestamps. |
| `SEED_DEMO_ACCOUNTS` | `1` | Seeds the demo student, 16 office accounts, and 7 subject-instructor accounts into an empty database. Set `0` for a clean install, then create accounts yourself. |
| `FACULTY_SIGNUP_CODE` | unset | When set, faculty self-registration is enabled and this value is the required access code. On Render, unset means faculty signup is **closed**. |
| `SESSION_COOKIE_SECURE` | `1` on Render, `0` locally | Send session cookies only over HTTPS. |
| `PORT` | `5000` | Injected by Render; used by gunicorn. |
| `GUNICORN_WORKERS` / `GUNICORN_THREADS` | `1` / `8` | Gunicorn process/thread counts. Keep workers at 1 with SQLite. |

### Backups
Render does not back up persistent disks automatically. From the Render Shell:

```bash
python -c "import sqlite3; s=sqlite3.connect('/var/data/eclearance.db'); d=sqlite3.connect('/var/data/eclearance-backup.db'); s.backup(d); d.close(); s.close()"
python -c "import sqlite3; print('\n'.join(sqlite3.connect('/var/data/eclearance.db').iterdump()))" > /var/data/eclearance-backup.sql
```

Copy the backup off the disk (Render Shell plus your storage CLI) before major changes.

### Before real use
- Change or remove every demo account. `credentials.txt` is for local reference only.
- Set a real `FACULTY_SIGNUP_CODE` (or keep faculty signup closed and create accounts yourself).
- For a database with no demo logins, set `SEED_DEMO_ACCOUNTS=0` **before the first boot**, then provision the office and instructor accounts you need (the 2nd Year flow requires the 7 instructor accounts and their `instructor_subjects` rows).
- Do not scale the service to multiple instances while using SQLite and the disk.

```bash
cd ~/chandy/chantot/web
pip install -r requirements.txt
python app.py
# open http://127.0.0.1:5000
```

DB file `eclearance.db` auto-creates on first run (SQLite, no setup). `gunicorn` is the production server and does not run on Windows; use `python app.py` locally. ## Production notes
- Sessions and CSRF tokens are signed with `SECRET_KEY`; Render generates it automatically.
- All forms are CSRF-protected with Flask-WTF.
- Security headers (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, HSTS on Render) are added to every response.
- Signature timestamps use `Asia/Manila`, not the server's UTC clock.
- SQLite runs in WAL mode with a 30-second busy timeout so reads and approval writes do not block each other.
- Keep a single web instance while SQLite is attached to the disk.
